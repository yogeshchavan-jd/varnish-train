    01 / THE COOKIE CARRIAGE

    Cookie comes in.
    Set-Cookie goes out.

    Cookie carries client state toward the application. Set-Cookie carries instructions back to the browser. Collecting request fields, choosing cache variants, and deciding whether to retain a response cookie are separate policy decisions.

    req.http.Cookie≠beresp.http.Set-Cookie
    02 / TWO DIFFERENT CACHES

    Stored by Varnish.
    Not by the browser.

    A cached object can retain its own freshness policy while the outgoing response receives different browser instructions. The example manifests show how delivery changes leave stored metadata intact.

    03 / THE GRACE CONNECTION

    Freshness expires.
    The journey can continue.

    Grace is an allowance for serving a stale object, not extra freshness. This demo assigns 30 minutes of example grace and illustrates a shorter serving window when the origin is healthy. Actual windows depend on policy and object availability.

    BEFORE YOU EVEN REACH VARNISH

    A few tracks
    go around the station.

    An edge server can choose another destination before cache processing begins. These are conceptual routing examples.

    LOCAL STATIC FILE

    Browser → edge → file

    An edge server may serve an existing file directly. Missing files can follow a separately configured fallback route.

    DIRECT APPLICATION ROUTE

    Browser → edge → application

    A selected application route can skip the cache service entirely. This differs from PASS, where Varnish still processes the transaction.

    PLAIN HTTP

    Browser → edge → redirect → HTTPS

    An edge may redirect a plain HTTP request to HTTPS. The browser’s follow-up is a new request with its own journey.

    Why normalization matters +

    Different URLs can describe the same content. This demo removes selected tracking parameters with a query-string parser, preserving business parameters and fragments. Matching is case-insensitive and empty tracking values are removed. These are illustrative choices, not production expressions.

    Built-in behavior and custom policy +

    Varnish provides built-in handling for request eligibility, hashing, and responses. Custom policies can add decisions or return before built-in processing. Stock cookie and authorization behavior can therefore differ from an application-specific policy. The workbench labels its illustrative choices explicitly.

    Hit-for-miss is not hit-for-pass +

    A cache miss with positive-lived uncacheable metadata can create hit-for-miss: a later cacheable response may replace it. Hit-for-pass explicitly bypasses lookup for subsequent matching requests during its lifetime. A transaction already in PASS does not become a reusable cached response.

    Order changes the outcome +

    An early return skips later decisions. Compare the cookie, path, and authorization services to see how much processing happens before PASS. The response workbench similarly shows why an early privacy decision can preserve a cookie that a later processing step would otherwise remove.

    Where this simulation draws the line +

    All domains, ports, request values, policies, ages, and transaction IDs are illustrative. The site contains no production VCL or Nginx configuration. It is a curated educational replay, not a VCL interpreter or live monitor. Background refresh is conceptual; no origin requests are made.
